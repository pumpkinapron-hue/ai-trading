## 2. AIの役割分担 — 研究はLLM、執行はルール

仕様書 §2.2 の「AIの役割」11項目は、性質の異なる2種類が混在している。これを明示的に分ける。

```
┌─ 研究レイヤー（LLM＝Claude等） ────────────────┐
│  市場データ解析 / パターン解析 / ニュース解析      │
│  トレーダー知見の整理 / 戦略候補の生成            │
│  バックテスト結果の分析 / 自己レビュー / 改善案    │
│         ↓ 出力するのは「決定論的なルール定義」      │
└──────────────────────────────────────────┘
                    ↓  人間が承認
┌─ 執行レイヤー（ルールエンジン） ──────────────┐
│  Market Regime判定 / BUY・SELL・WAIT           │
│  TP・SL算出 / リスク管理 / 発注                 │
│         ↓ 同じ入力 → 必ず同じ出力                │
└──────────────────────────────────────────┘
```

**なぜ分けるか。** LLMは同じ入力に対して同じ出力を返さない。執行判断をLLMが直接行うと、
バックテストで測った期待値と実運用の挙動が原理的に一致しなくなり、仕様書 §14（過学習対策）と
§22（実運用への移行条件4「取引コスト込みでプラス期待値」）が検証不能になる。
また1分足で毎バーLLMを呼ぶのはコストとレイテンシの両面で成立しない。

**仕様書 §16「AI判断ログ」への影響。** ログの「Reasons」は、LLMが自由文で書いたものではなく、
**発火したルールの列挙**になる。これは仕様書の意図（人間が後から妥当性を検証できる）に対して
むしろ強い。自由文の理由は検証も再現もできないが、ルールなら過去データ全体に遡って適用できる。

**仕様書 §20「自己改善ループ」への影響。** ループは以下になる。

```
結果 → LLMがレビューし改善案とルール定義を出力
     → ルールエンジンでバックテスト → OOS検証 → フォワード
     → 人間が承認 → 新バージョン採用
```

LLMが実運用戦略を直接書き換えることは、仕様書 §20 のとおり禁止する。

### 2.1 執行パスのレイテンシと、LLMを入れない保証

```
1分足が確定（毎分00秒）
      ↓  数ms          ルールエンジンが指標計算・条件判定
BUY / SELL / WAIT + TP/SL 決定
      ↓  数十〜数百ms   ネットワーク・ブローカー
発注
```

合計1秒未満。LLMを挟むと5〜15秒かかり、1分足でも次の足に食い込む。

**方針を書くだけでは守れないので、テストで縛る。** 執行系モジュール
（`execution/` `risk/` および戦略評価のホットパス）が `anthropic` / `openai` などの
LLMクライアントを import していないことを依存方向テストで検査する。
入れようとした時点でテストが落ちる。

**残る構造的な遅延（LLMとは無関係）。** 本設計は1分足の確定を待って判断するため、
「バー確定 → 発注」に最大1分の間が空く。ティックに即応する作りではない。
数秒〜数十秒のスキャルピングはレイテンシ勝負になり個人が勝てる土俵ではないため、
仕様書 §5 の想定（最短1分足）に合わせてこの設計を採る。この時間軸では数百msの遅れは
期待値にほぼ影響せず、スプレッドのほうが桁違いに効く。

### 2.2 研究レイヤーのモデル割り当て

頻度と難易度で割り当てる。戦略発案は低頻度なので最上位モデルを使ってもコストが効かない。
逆に毎トレードのレビューを最上位モデルで回すと積み上がる。

| タスク | 頻度 | モデル | effort |
|---|---|---|---|
| 戦略の発案・仮説生成 | 週数回 | `claude-fable-5` | `max` |
| バックテスト結果の分析・失敗要因分析 | 週数回 | `claude-opus-5` | `xhigh` |
| トレードごとの定型レビュー | 毎トレード | `claude-sonnet-5` | `medium` |
| 動画文字起こしからの知識抽出 | 中頻度 | `claude-sonnet-5` | `high` |
| ニュース分類・影響度タグ付け | 日次多数 | `claude-haiku-4-5` | — |

月額の概算は合計 $38 程度（戦略発案 $16 / バックテスト分析 $9 / トレードレビュー $8 /
ニュース分類 $5）。市場データのサマリと戦略履歴は毎回同じものを送るため、
プロンプトキャッシュで入力側は約9割減る。

**モデルIDは `config/settings.toml` に書き、コードに直書きしない。** 新しいモデルが出たときに
1箇所で切り替えられるようにする。

### 2.3 LLM出力は構造化出力で受ける

戦略発案の結果を自由文で受け取るとルールエンジンに流せない。構造化出力で
機械可読なルール定義（条件式・TP/SL・対象時間軸・対象セッション）として受け取り、
そのままバックテストにかけられる形にする。人間が承認する対象もこれになる。

仕様書 §19 の戦略バージョン管理には `generated_by`（モデルID・effort・プロンプトのハッシュ・
生成時刻）を記録する。後から「この戦略はなぜ採用されたのか」を追うために要る。

**モデルの性能は検証の厳しさを代替しない。** 性能の高いモデルは良い仮説を多く出すが、
当たりを引く保証はない。むしろ賢いモデルほど「もっともらしいが実際には効かない話」を
説得力をもって書ける。検証の門（バックテスト → OOS → フォワード → 人間承認）は、
モデルが良くなっても緩めない。

## 3. データ層

### 3.1 データソースの抽象化

```python
class BarSource(Protocol):
    def fetch(
        self, symbol: str, timeframe: Timeframe,
        start: datetime, end: datetime,
    ) -> pd.DataFrame: ...
```

返す DataFrame のスキーマを固定する。

| 列 | 型 | 内容 |
|---|---|---|
| `open_time` | datetime64[ns, UTC] | バー開始時刻（tz-aware） |
| `close_time` | datetime64[ns, UTC] | バー終了時刻 |
| `bid_open` / `bid_high` / `bid_low` / `bid_close` | float64 | Bid側OHLC |
| `ask_open` / `ask_high` / `ask_low` / `ask_close` | float64 | Ask側OHLC |
| `volume` | float64 | 出来高（Dukascopyはティック数ベース） |

**Bid/Ask を両方持つ理由。** mid に丸めると、買いはAsk・売りはBidで約定するという事実を
バックテストで再現できなくなる。仕様書 §9 の「期待利益 − 取引コスト」が検証できなければ
Phase 0 を作る意味がない。1分足10年分でも 300MB 程度であり、容量は問題にならない。

### 3.2 データソースの選定

| 候補 | 履歴 | Bid/Ask | 発注 | 口座 | 判定 |
|---|---|---|---|---|---|
| **Dukascopy** | 2005〜、ティック | 両方 | 不可 | 不要 | **採用** |
| OANDA v20 | 十分 | 両方 | 可 | 必要 | Phase 2で追加検討 |
| MetaTrader5 | ブローカー依存 | Ask側が弱い | 可 | 必要 | Phase 2で追加検討 |
| HistData | 2000〜、分足 | Bidのみ | 不可 | 不要 | 補助 |

Dukascopy を選ぶ理由は、口座開設なしで即着手でき、Bid/Ask両方のティックが2005年から無料で取れ、
データ品質が業者配信より良いこと。実装は PyPI の `dukascopy-python` を第一候補とし、
動作が不安定なら `.bi5` の直接ダウンロードに切り替える。**いずれもアダプタ内部の話であり、
上位層は影響を受けない。**

### 3.3 保存形式

```
data/
├── bars/{symbol}/{timeframe}/{year}.parquet   # バーデータ
├── raw/ticks/{symbol}/{year}/{month}.parquet  # ティック（将来）
└── meta.db                                     # SQLite
```

SQLite（`meta.db`）が持つもの:

- `fetch_ranges` — シンボル・時間軸ごとの取得済み区間（再取得の冪等性を担保）
- `quality_reports` — 品質チェック結果（§6）
- 将来: トレードログ、戦略バージョン、AI判断ログ（仕様書 §15/§16/§19）

**PostgreSQLを採らない理由。** 単一利用者・単一マシンで、書き込みは日次バッチ、
読み出しは時系列レンジスキャンが中心。この形状では列指向ファイル（Parquet）が
サーバー型RDBより速く、かつ移行がフォルダのコピーで済む。移行前提の要件に直接効く。

### 3.4 時間軸の識別子

`{timeframe}` に入る値を固定する。日足・週足は §4.2 の2系統ぶん存在する。

```
1m  5m  15m  1h  4h  1D_ny  1D_jst  1W_ny  1W_jst
```

`1m` のみをデータソースから取得し、他はすべて `1m` から生成する（§5 第3層の規約に従う）。
生成物であることを保証するため、`5m` 以上は「1分足から再生成すれば必ず同じものができる」
状態を維持する（テストで担保。§11）。

### 3.5 初期データスコープと期間分割

| 項目 | 値 |
|---|---|
| 通貨ペア | USD/JPY のみ |
| 取得粒度 | 1分足（Bid/Ask） |
| 取得期間 | 2015-01-01 〜 現在 |
| 想定サイズ | Parquet圧縮後で 300〜500MB 程度 |

**2015年を開始点とする理由。** レジームの多様性を確保しつつ、市場構造が現在と連続している
範囲に限る。この期間には 2015年チャイナショック、2016年 日銀マイナス金利・Brexit・米大統領選、
2019年1月 フラッシュクラッシュ、2020年 コロナショック、2022年以降の日米金利差拡大と為替介入、
2024年 キャリー巻き戻しが含まれる。それ以前（2008年など）はスプレッド水準と執行環境が
現在と大きく異なるため、優位性の検証に使うと誤った結論を招きやすい。必要になれば後から
遡って追加取得できる設計にする。

**期間分割**（`config/settings.toml` に定義）:

| 区分 | 期間 | 扱い |
|---|---|---|
| Training | 2015-01-01 〜 2021-12-31 | 自由に分析してよい |
| Validation | 2022-01-01 〜 2023-12-31 | 戦略候補の絞り込みに使う |
| Out-of-Sample | 2024-01-01 〜 2026-08-24 | **ロック**。解除には明示フラグと記録が必要 |
| Forward | 2026-08-25 以降 | 実時間で前進する。過去には存在しない |

Forward 区間の開始を本設計の日付に置くことで、Forward は定義上「一度も見ていないデータ」になる。

### 3.6 `as_of` カーソル（先読み防止 第4層）

データアクセスAPIをこれ一本にする。

```python
lake.load(symbol, timeframe, as_of: datetime) -> pd.DataFrame
```

`as_of` より後の `close_time` を持つバーは**物理的に返さない**。バックテストおよび
フォワードテストはこのAPIしか使えないため、時点Tのシミュレーション中に未来のデータを
メモリに載せること自体が不可能になる。

## 4. 時刻基盤 — 日本基準とNY基準を並列に持つ

### 4.1 保存

すべて **UTC の tz-aware**。naive datetime はテストで全面禁止する。

### 4.2 日境界（日足・週足の区切り）

2系統を別々に生成し、別々に保存する。どちらか一方を選ぶ設計にはしない。

| 系統 | 区切り | DST | 保存先 |
|---|---|---|---|
| `NY_CLOSE` | 17:00 `America/New_York` | 自動追従（夏 21:00 UTC / 冬 22:00 UTC） | `bars/{sym}/1D_ny/` |
| `JST` | 00:00 `Asia/Tokyo` | なし（固定 15:00 UTC） | `bars/{sym}/1D_jst/` |

同じ1分足から2通りの日足が生成される。「NY基準では陽線だが日本基準では陰線」といった差も
そのまま分析対象になる。週足も同様に2系統（NY: 日曜17:00 NY〜金曜17:00 NY / JST: 月曜0:00〜）。

Phase 4 の日本株では JST 系統が必須になるため、いずれ必要になる作りでもある。

### 4.3 セッションラベル

各バーに市場時間帯のタグを付ける。仕様書 §1「時間帯による市場環境の変化を研究できる」が狙い。

| ラベル | 定義（各市場のローカル時刻） |
|---|---|
| `TOKYO` | 09:00–17:00 `Asia/Tokyo` |
| `LONDON` | 08:00–16:30 `Europe/London` |
| `NEWYORK` | 08:00–17:00 `America/New_York` |
| `LDN_NY_OVERLAP` | LONDON ∩ NEWYORK（最も出来高が出る帯） |
| `OFF` | いずれにも該当しない（東京早朝の薄商い帯など） |

**UTCの固定時刻では定義しない。** 各市場のローカルタイムゾーンで定義してから都度UTCへ変換する。
固定オフセットで書くと、夏時間の切り替え週に1時間ずれた分析をすることになる。

### 4.4 市場の開閉

金曜クローズ〜日曜オープンは「市場閉鎖」として明示的に扱い、**欠損と区別する**。
区別しないと、品質チェック（§6）が毎週末に偽陽性を出して機能しなくなる。

## 5. 先読みバイアスの構造的排除

「気をつける」では守れない。**書こうとしても書けない**構造にする。4層で担保する。

### 第1層 — 確定足しか分析APIに出てこない

各バーは `open_time` / `close_time` / `is_closed` を持つ。分析系APIは `is_closed == True`
のバーしか返さない。形成中の足は別経路（リアルタイム監視用）でしか触れないため、混入しない。

### 第2層 — トランケーション不変性テスト

全指標に機械的に適用する検査。

> 入力データの末尾を k 本切り落としても、残った部分の出力が1つも変わらないこと

先読みしている指標はこれで必ず落ちる。`center=True` のローリング窓、将来のバーを見た正規化、
全期間統計を使った標準化は、すべて検出される。

pytest でパラメトライズし、**指標レジストリに登録された全関数へ自動的に適用**する。
新しい指標を追加したら、テストを書き忘れても自動で検査対象に入る。

### 第3層 — リサンプルの時刻規約

1分足から5分足を作るとき、その5分足が利用可能になるのは**5分が終わった瞬間**である。
`close_time = open_time + period` を必ず持たせ、参照は常に `close_time` 基準で行う。

マルチタイムフレーム解析（仕様書 §5）での先読みは、ここを誤るのが典型的な原因である。
「4時間足が上昇トレンド」という情報を、その4時間足の確定前に知ることはできない。

### 第4層 — `as_of` カーソル

§3.6 のとおり。

**効き方の違い**: 第2層は指標の実装ミスを、第4層はバックテストエンジンの設計ミスを潰す。
両方必要である。

## 6. データ品質チェック

取得直後に自動実行し、結果を `meta.db` の `quality_reports` に記録する。

| 検査 | 内容 |
|---|---|
| バー数照合 | 市場カレンダー基準の想定本数 vs 実本数 |
| 欠損区間 | 連続欠損の最長区間と一覧 |
| スプレッド異常 | ゼロ・負・異常に広い（分位点基準） |
| 価格ジャンプ | ATRのN倍を超える変化 |
| 重複 | 同一 `open_time` の重複 |

バックテスト時に「品質NG区間を除外する」指定ができるようにする。
仕様書 §21 の「データ欠損時停止」の判定ロジックはここを土台にする。

## 7. テクニカル指標

### 7.1 自前実装とする

TA-Lib はビルド済みバイナリを必要とし、Windows間の移行で詰まりやすい。
ただし**移植性は主たる理由ではない**。本当の理由は、全指標を「時点tまでの情報しか使わない」で
統一し、第2層のトランケーション不変性テストで機械的に縛れるようにするため。
外部ライブラリでは、この保証を自分たちで持てない。

初期実装: SMA / EMA / RSI / MACD / ATR / ボリンジャーバンド / VWAP / 期間高値安値 / ヒストリカルボラティリティ。

### 7.2 正しさの検証（参照値照合）

自前実装が正しい値を返すことを担保する。既存ライブラリ（`ta` 等）の出力と一度照合し、
**ゴールデン値としてフィクスチャに固定**する。以降はライブラリに依存せず、フィクスチャと比較する。

ここが狂うと以降の分析が全部崩れるため、指標ごとに実施する。

## 8. 期待値スキャン（`edge_scan`）

**バックテストエンジンではない。** TP/SL もポジション管理も資金管理も持たない、純粋な統計モジュール。
バックテストエンジンを作る前に「そもそもこの指標に優位性の種があるか」を見るために使う。

```
条件を定義（例: RSI(14) が 30 を下抜けた確定足）
      ↓
その後 +1 / +5 / +15 / +30 / +60 バーのリターンを集計
      ↓
サンプル数・平均・中央値・勝率・標準偏差・信頼区間
```

設計上ゆずれない点が3つある。

**(1) スプレッド控除後で評価する。** 生のリターンで見ると、ほとんどの指標が有望に見える。
仕様書 §9 の「期待利益 − 取引コスト」を最初から適用し、実際に取れる分だけを表示する。

**(2) セッション別・時間帯別に層別集計する。** §4.3 のセッションラベルがここで効く。
「RSI逆張りは東京時間では効くがロンドン時間では逆効果」といった差は、全期間を平均すると消える。

**(3) OOS期間はデフォルトでロックする。** 集計対象は Training 期間のみ。OOS期間を見るには
明示的なフラグが必要で、その解除は `meta.db` に記録を残す。

仕様書 §14 の過学習対策は、人間が「ちょっとだけ覗く」のを防げないと機能しない。
**人間が一度OOSの結果を見てしまったら、そのOOSはもうOOSではない。** 仕組みで縛る。

期間分割は §3.5 の定義（`config/settings.toml`）に従う。

## 11. テスト方針

| 対象 | 内容 |
|---|---|
| バー集約 | 境界条件（バー境界ちょうどのティック）、空バーの扱い |
| リサンプル整合 | **1分足から生成した5分足 == Dukascopyから直接取得した5分足**。検証専用に5分足を一度だけ取得して照合する（保存対象は1分足のみ。§3.4） |
| 指標 | ゴールデン値照合（§7.2） |
| 先読み | 全指標へのトランケーション不変性テスト（§5 第2層） |
| 時刻 | DST切り替え日（3月・11月）の日境界、セッション境界 |
| 品質 | 人工的な欠損・異常値を仕込んで検出できるか |
| `as_of` | `as_of` より後のデータが返らないこと |
| 依存方向 | 執行系モジュールがLLMクライアントを import していないこと（§2.1）。Phase 0では対象モジュールが存在せず自明に通るが、**誘惑が生まれる前に**入れておく |
